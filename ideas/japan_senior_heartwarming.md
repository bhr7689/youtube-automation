## 🔧 기술 스택 (예상)

### 데이터 수집
- **YouTube Data API v3** — 채널·영상 메타데이터
- **yt-dlp** — 원본 영상 다운로드 (저작권/페어유스 검토 필요)
- **youtube-transcript-api** — 자막 수집
- **Whisper (OpenAI API)** — 자막 없을 때 STT 백업

### 분석·추출
- **Gemini** — "가장 감동적인 30초~1분 구간" 자동 식별 (자막+장면 단서)
- 컷 후보 스코어링: 키워드 매칭(가족·눈물·감사·도전) + 댓글 감정 분석

### 번역·TTS
- **DeepL API** 또는 Gemini — 영→일 번역 (시니어 친화 어휘)
- **TTS 후보**:
  - Google Cloud TTS (일본어 자연스러움 ★)
  - Azure Speech (감정 톤 조절 가능)
  - ElevenLabs (가장 자연스럽지만 비쌈)
  - VOICEVOX (무료 일본어 TTS, 시니어 톤 가능)

### 편집·합성
- **CapCut** 자동화 옵션:
  - **CapCut Desktop API/Plugin** — 공식 API 없음. 템플릿 JSON 직접 생성?
  - **CapCut Web 자동화** — Playwright로 UI 조작 (가능하나 fragile)
  - **대안 1: ffmpeg 직접** — 우리 `media_core.py` 확장 (제어력 ★)
  - **대안 2: Remotion** — React 기반 프로그래밍 비디오 (시니어 자막 UI 예쁘게)
  - **대안 3: Shotstack API** — 클라우드 비디오 편집 (월 구독)

### 후처리
- 따뜻한 톤 LUT 자동 적용 (ffmpeg color filter)
- 잔잔한 BGM 자동 매칭 (라이선스 음원 라이브러리 필요)
- 일본어 자막 자동 동기화 (기존 `media_core.generate_srt` 활용)

## ⚠️ 검토 필요 (리스크)

1. **저작권** — 원본 영상의 인용 범위·페어유스. 일본 유튜브의 저작권 클레임 정책 확인 필수.
2. **CapCut 자동화** — 공식 API가 없음. 직접 ffmpeg/Remotion이 더 안정적일 수 있음.
3. **TTS 비용** — 일일 영상 1편 × 5분 = 한 달 5천원~5만원 범위 (서비스에 따라).
4. **번역 품질** — 시니어가 거부감 없는 일본어 톤 (です/ます 정중체 + 따뜻한 어휘).

## 🛡️ 대본 3중 게이트 설계 (2026-07-02 — 컷편집 자동화의 안전장치)

> 요구: ① 유튜브 알고리즘이 끌어당기는 대본 ② 유사 대본·유사 영상 판정 회피
> ③ 허위 콘텐츠 낙인 방지. → 대본 생성 후 3개 게이트를 직렬 통과해야만 TTS·컷편집 진행.

```
대본 생성(Gemini)
  → [게이트1 🎯 알고리즘 적합도 채점]   미달 → 재생성(1회)
  → [게이트2 🔍 유사도 검사]            초과 → 구조 바꿔 재생성(1회)
  → [게이트3 ✅ 사실 검증(환각 검사)]    실패 → 근거 없는 문장 수정/삭제
  → 전부 통과 → TTS·컷편집 // 재시도 실패 → 사람 검수 큐
```

### 게이트1 🎯 끌어당기는 대본 (retention 설계)
- **데이터 기반 훅**: 원본 영상의 댓글 타임스탬프·"다시 본 구간" 언급 분석 → 감정 피크 지점에서 훅 추출 (K-Trot score.py 댓글 분석 패턴 재사용)
- **대본 구조 템플릿**: 3초 훅 → 궁금증 루프(결말 암시) → 전개 → 클라이맥스 → 여운.
  시니어용 변형: 느린 템포, 정중체, 중간 요약 반복(이탈 방지), 마지막 긍정 어휘("お疲れさまでした")
- **삼위일치 원칙**: 제목·썸네일·대본 내용 일치 — 낚시 불일치는 알고리즘이 이탈률로 감지해 오히려 페널티
- **셀프 평가 루프**: `lyrics_evaluator.py` 패턴 이식 — 4기준(훅 강도/감정 곡선/시니어 적합/삼위일치) 0~10 채점, 임계 미달 시 자동 재생성

### 게이트2 🔍 유사도 방어 (재사용·반복 양산 판정 회피)
- **대본 유사도 검사기**: 임베딩(또는 n-gram) 비교 대상 2개 —
  ① 내 과거 대본 전부(자기복제 방지) ② 수집해둔 경쟁 채널 대본 DB(표절 판정 방지).
  임계값 초과 시 "구조를 바꿔서" 재생성 (표현만 바꾸는 게 아니라 전개 순서 변경)
- **구조 로테이션**: 대본 템플릿 5~6종을 돌려가며 사용 — "반복 양산 콘텐츠" 판정 회피
- **영상 변형(대본 밖 요소)**: 원본 그대로 업로드 금지. 줌·크롭·속도·자막·B롤 삽입·화면 분할 + 원본 오디오 최소화(내레이션+BGM 중심 재구성) = "실질적 변형" 확보
- **⚠️ 정직한 한계**: Content ID(영상·음성 지문)는 대본으로 못 막음. Oprah/Ellen/Dr.Phil급 대형 쇼는 지문 등록돼 있어 걸릴 확률 높음 → **근본은 소스 전략**: CC/허가 소스 우선, 클립 짧게, 변형 크게, 수익공유 감수 여부 사전 결정

### 게이트3 ✅ 허위 콘텐츠 방어 (사실 그라운딩)
- **입력 제한 생성**: 대본 생성 입력 = 원본 자막 + 메타데이터만. 프롬프트에 "원본에 없는 사실 창작 금지" 명시
- **검증 패스(환각 검사)**: 생성된 대본의 문장별로 원본 자막과 대조 — 근거 없는 문장은 자동 수정/삭제 (2차 LLM 호출)
- **완충 표현 규칙**: 단정 대신 "~라고 합니다/전해집니다" — 연출·추정을 사실처럼 말하지 않기
- **민감 주장 필터**: 의료·재정·정치 단정 문장 자동 차단
- **증거 보관**: 영상마다 소스 원본 URL + 타임스탬프 + 자막 원문을 메타로 저장 → 분쟁·이의제기 시 근거 제출용

### ✂️ 자동 컷편집 확정 스펙 (2026-07-02 사용자 확정)
- **유일한 흐름: 원본 롱폼 → 쇼츠(세로)**. 롱폼→롱폼, 쇼츠→쇼츠 재편집은 범위 밖.
- **변형 규칙 (기본 내장, 끄기 불가 수준의 원칙)**:
  1. **확대(줌/크롭)** — 원본 프레임 그대로 노출 금지
  2. **좌우 반전(미러)**
  3. **동일 원본 구간 5초 이상 연속 사용 금지** — 컷 플래너가 대본 문장 단위로
     3~5초 서브클립을 배분하고, 같은 구간을 다시 쓸 땐 다른 변형(줌 비율·반전 여부)을 적용
  4. (기존 결정과 결합) 원본 오디오 최소화 + TTS 내레이션 + BGM + 일본어 자막 burn-in
- **컷 플래너 로직(설계)**: JP 대본 문장별 필요 길이 산출 → 원본에서 장면 후보 매칭 →
  3~5초 세그먼트로 쪼개 배치 → 세그먼트마다 변형 파라미터(줌 1.1~1.3배, 반전 on/off,
  속도 0.95~1.05배) 자동 다양화 → 타임라인 생성
- **Claude 추가 변형 팔레트(제안)**: 따뜻한 톤 LUT(기결정) · 배경 블러 패딩(가로→세로 변환 시) ·
  자막 바/테두리 오버레이 · 미세 속도 변화 · 장면 순서 재배열(대본 논리 우선)
- **CapCut 연동 방식 ✅ 확정(2026-07-02): A안 — CapCut 초안(draft) 자동 생성**
  - 흐름: 자동 컷편집 엔진이 컷 플랜 완성 → **CapCut 프로젝트(draft)로 내보냄** →
    사용자가 CapCut 데스크톱에서 열어 **손맛 마무리** → CapCut에서 최종 내보내기
  - **핵심 원칙: 변형을 영상에 굽지(bake) 않는다** — 줌·반전·속도·컷 경계·자막·오디오를
    전부 **CapCut 트랙/클립 속성으로 표현** → 사용자가 CapCut에서 자유롭게 수정 가능
    · 컷 = 타임라인 세그먼트(원본 참조) · 줌/반전/속도 = 클립 속성
    · 일본어 자막 = 텍스트 트랙 · TTS 내레이션/BGM = 오디오 트랙(볼륨 커브 포함)
  - 구현 후보: draft_content.json 직접 생성 (pyJianYingDraft 계열, 비공식)
  - ⚠️ 리스크: draft 포맷이 CapCut 버전마다 다름 → **사용자 CapCut 버전 고정 + 버전 확인 필요**
  - 백업 경로: draft 생성이 깨지는 버전을 만나면 ffmpeg 자동 렌더본(B안)을 예비로 제공

### 🌸 일본어 번역봇 → ✂️ 컷편집 연동 설계 (2026-07-02)

> 포털 시안 정의: "영어/한국어 대본을 일본어 쇼츠로 자동 변환 + TTS".
> 핵심 질문: 번역·TTS 결과를 **어떤 형태로 저장·다운로드해야 컷편집이 그대로 쓰나**.

#### 처리 흐름 (5단계)
```
① 입력   대본(한/영) 붙여넣기 or RefTracker 자막 가져오기(🔗 도구 연결)
② 번역   Gemini — 시니어 정중체(です/ます) + 완충 표현 + 금지어 필터 (게이트3 규칙 공유)
③ 검수   문장별 카드 UI — 개별 수정·재번역. 문장 = 이후 모든 단계의 기본 단위
④ TTS   ⭐ 문장별 개별 합성 (한 덩어리 금지!) → 문장마다 정확한 길이(duration) 확보
⑤ 패키지 narration job 폴더 생성 → 서버 보관 + ZIP 다운로드
```

#### 📦 패키지 구조 (narration job) — 컷편집의 입력 규격
```
naration_job_{id}/
├── manifest.json        ← 총괄 매핑 (아래 스키마)
├── script_jp.txt        ← 전체 일본어 대본 (사람용)
├── audio/
│   ├── 001.wav … NNN.wav   ← 문장별 TTS (48kHz 16bit mono WAV)
│   └── full.wav            ← 전체 합본 (미리듣기·백업용)
└── subtitle.srt         ← 문장 duration 누적으로 자동 생성한 일본어 자막
```

#### manifest.json 스키마 (핵심)
```json
{
  "job_id": "nj_20260702_001", "voice": "voicevox:tohoku_kiritan",
  "language": "ja", "created_at": "…", "source_script_lang": "ko",
  "total_duration_ms": 58300,
  "sentences": [
    { "id": 1, "src": "40년 만에 어머니를 만났습니다",
      "jp": "40年ぶりに母に会いました",
      "audio": "audio/001.wav", "duration_ms": 3120,
      "pause_after_ms": 300, "emphasis": "hook" }
  ]
}
```

#### 왜 "문장별 개별 TTS"가 핵심인가
1. **컷 플래너의 입력** — 문장 duration이 있어야 "이 문장에 3~5초 서브클립 몇 개" 배분 가능
2. **CapCut draft 에서 문장 = 개별 오디오 클립** — 손맛 마무리 때 문장 단위로 이동·교체 가능
3. **부분 재작업** — 한 문장만 어색하면 그 문장만 재번역·재합성 (전체 재생성 불필요)
4. **자막 자동 동기화** — duration 누적만으로 SRT 완성 (forced alignment 불필요)

#### 포맷 결정
- 오디오: **WAV 48kHz 16bit mono** (편집용 무손실) + UI 미리듣기용 mp3
- 자막: SRT (문장 duration + pause 누적) — CapCut 텍스트 트랙 변환도 manifest 기반
- 음성: 채널 시그니처당 **1개 목소리 고정** (정체성)
- **TTS ✅ 확정(2026-07-02): VOICEVOX** — 무료·로컬 실행·일본어 특화·WAV 직출.
  로컬 HTTP 서버(기본 포트 50021)로 구동 → FastAPI 가 문장별 합성 요청.
  화자(speaker) 목록에서 시니어 친화 톤 선정은 실제 청음 후 결정(사용자 귀 검수).
  속도·억양·pause 파라미터 조절 가능 → 시니어용 "약간 느리게" 프리셋 기본값.

#### 전달 경로
- 도구가 같은 앱 안에 있으면: **job_id 로 내부 전달** (다운로드 불필요) — 컷편집 화면에서
  "🌸 번역봇 작업 불러오기" 드롭다운
- 분리 실행/백업: **ZIP 다운로드** → 컷편집 inbox 폴더에 투입 (K-Trot pipeline.py 의
  inbox 감시 패턴 재사용)
- ✂️ 컷편집은 manifest.json 만 읽으면 됨 — 문장·시간·오디오·자막이 전부 담겨 있음

### 🖥️ 기술 스택 ✅ 확정(2026-07-02): B — Next.js + FastAPI
- 실행 형태: 사용자 PC에서 bat 1개로 프론트+백엔드 동시 기동 (유튜브실행.bat 방식)
- FastAPI(파이썬)가 기존 자산(YouTube API·Gemini·transcript_probe·media_core) 재사용
- 아래는 결정 당시 비교표 (기록 보존용)
| | A. Streamlit | B. Next.js + FastAPI (추천) |
|---|---|---|
| 시안 재현도 | 6~7할 (카드·칩 흉내 가능, 투박) | 10할 (목업 그대로) |
| 반응 속도 | 클릭마다 전체 재실행(무거움) | 즉각 (필터·정렬 브라우저 처리) |

| 실행 형태 | bat 1개 | bat 1개 (프론트+백엔드 동시 기동) 가능 |

- **사이드바 메뉴**: 🔥 트렌드 피드 / 🌐 YouTube 발굴 / 🔍 검색 / 📺 레퍼런스 채널 / 📁 컬렉션 / ⭐ 북마크 / 🔔 알림 / ⚙️ 설정

- **결과 카드**: SHORTS 뱃지 · 배수(×N) 뱃지(등록 채널만) · +추가/✓등록 · 액션 5개(자막/원본/유사/댓글/링크)

### 카드 그리드 공통 디테일 (시안 추가 확인)
- 우상단 범례: **카드 상단 색 띠** = ✓ 이미 등록된 채널(초록) / + 새로 추가할 채널(핑크)

### 🆕 신생 채널 필터 (2026-07-02 요구)
- 검색 결과에서 **개설 6개월 이내 채널만** 모아 보는 필터/탭
- 표시는 기존 검색 결과와 **동일한 카드 그리드** 그대로
- 구현 근거: YouTube API `channels.list → snippet.publishedAt` (채널 개설일)
- 설계 제안: 기간 칩 `1개월 / 3개월 / 6개월 / 12개월 이내` 선택식 (기본 6개월)
- 카드에 `🌱 개설 N개월` 뱃지 추가 → 신생인데 배수 높으면 = 최우선 벤치마킹 대상
- 신생 채널 + 급등 배수 조합 = "히든 젬 레이더"의 핵심 시그널
