# 🕵️ 원본 롱폼 → "제일 처음 숏폼화한 영상" 찾기 — 상세 기획

> 사장님 요구: **원본 롱폼 영상을 가장 먼저 숏폼화(쇼츠화)한 영상의 링크를 반드시 찾아 보여줘야 한다.**
> 이 문서 = 그 기능의 현실적 설계 + 신뢰도 정직 고지 + 단계별 구현 계획.

---

## 0. 먼저 — 정직한 한계 (아주 중요)

**"우주에서 제일 처음"을 100% 증명하는 것은 기술적으로 불가능합니다.** 이유:

1. **삭제·비공개**: 진짜 최초 쇼츠가 이미 삭제됐거나 비공개면 세상 어디에도 흔적이 없다.
2. **정확한 업로드 시각 비공개**: YouTube API 는 `publishedAt`(날짜+시각)을 주지만, **재업로드·백데이팅**이
   가능하고, 틱톡/인스타/더우인은 시각 체계가 제각각이라 **플랫폼 간 '누가 먼저'를 초 단위로 비교 불가**.
3. **전역 색인 없음**: "이 롱폼에서 파생된 모든 쇼츠 목록" 같은 DB 는 세상에 없다. 검색으로 긁어모아야 함.
4. **매칭은 확률**: "이 쇼츠가 정말 그 롱폼에서 나왔나?" 는 영상·오디오 지문(fingerprint)으로 판정 →
   100% 가 아니라 **신뢰도 %**.

### 그래서 우리가 실제로 보장하는 것
> ❌ "우주 최초" 단정
> ✅ **"지금 공개적으로 확인 가능한, 이 롱폼에서 파생된 가장 이른 쇼츠"** 를
>    **근거 + 신뢰도(HIGH/MEDIUM/LOW) + 타임라인**과 함께 제시.
>    그리고 "이보다 이른 삭제·비공개본이 존재할 수 있음"을 항상 명시.

이것이 Codex(사장님이 쓰던 source-finder)와 동일한 철학 — **"가장 이른 공개 후보"를 분리 판정**.

## 1. 현재 자산 vs 목표 (무엇이 있고 무엇이 없나)

| 단계 | 현재 `source_finder.py` | 목표(원본→최초 쇼츠)에 필요 | 상태 |
|---|---|---|---|
| 메타 수집(yt-dlp/oEmbed) | ✅ 있음 | 그대로 | 🟩 |
| 480p 다운로드·프레임·워터마크 스트립 | ✅ 있음 | 그대로 | 🟩 |
| @핸들 추출(정규식+OCR) | ✅ 있음 | 그대로 | 🟩 |
| 5플랫폼 후보(프로필·검색·DDG) | ✅ 있음 | 그대로 | 🟩 |
| "가장 이른 공개 후보" 판정 | ✅ 일부 | 강화 필요 | 🟨 |
| **원본 롱폼 ↔ 쇼츠 연결(파생 판정)** | ❌ 없음 | **신규** | 🟥 |
| **파생 쇼츠 전수 수집 + 날짜순 정렬** | ❌ 없음 | **신규** | 🟥 |
| **영상/오디오 지문 매칭(진짜 파생인지 검증)** | ❌ 없음 | **신규** | 🟥 |
| **타임라인(누가 언제 숏폼화)** | ❌ 없음 | **신규** | 🟥 |

→ **골격은 있음. 진짜 만들 것 = 파생 판정 + 전수 수집 + 지문 매칭 + 타임라인.**

## 2. 파이프라인 (상세 설계)

입력: ① 쇼츠 URL(이걸로 원본을 거슬러 올라감) 또는 ② 원본 롱폼 URL(이걸 숏폼화한 것들을 찾음).

```
[입력] 쇼츠 or 롱폼 URL
   │
   ├─ A. 지문 추출(Fingerprint) ── 이 영상의 '고유 지문'을 뜬다
   │      · 메타(제목/설명/업로더/업로드일/길이)  ← yt-dlp
   │      · 키프레임 + pHash(perceptual hash, 화면 지문)
   │      · 오디오 지문(chromaprint/fpcalc)  ← 배경음·대사 동일성
   │      · 자막(대사 텍스트)  ← transcript_probe 재사용
   │      · OCR(화면 글자) + 워터마크 @핸들  ← 기존 source_finder 재사용
   │
   ├─ B. 원본 롱폼 후보 찾기 (입력이 쇼츠일 때)
   │      · 워터마크 @핸들 → 그 채널의 '긴 영상'들
   │      · 설명란 크레딧/원본 링크
   │      · 키프레임 역이미지 검색(Google Lens/DDG)
   │      · 자막 인용구 검색(구글/유튜브) → 원문 롱폼
   │      · 후보 중 [길이 김 + 지문 포함 + 날짜 이름] = 원본 롱폼
   │
   ├─ C. 파생 쇼츠 전수 수집 (Derivatives)
   │      · YouTube Data API 검색: 원본 제목·주제·인용구·핸들로
   │        → **날짜 오름차순(오래된 순)** 정렬해 긁기
   │      · (옵션) 틱톡/인스타/더우인 검색 루트(핸들·키워드)
   │      · 각 후보 쇼츠: {url, 채널, publishedAt, 썸네일}
   │
   ├─ D. 매칭 검증 (진짜 그 롱폼에서 나왔나?)
   │      · 각 후보의 pHash/오디오 지문 ↔ 원본 롱폼 구간 대조
   │      · 신뢰도 점수(0~100) + 매칭 구간(원본 몇 분~몇 분)
   │      · 우연 일치·무관 영상 걸러냄(임계 미만 탈락)
   │
   ├─ E. "제일 처음" 판정
   │      · 검증 통과분만 → publishedAt 오름차순 → 최상단 = 최초 숏폼화
   │      · 근거 우선순위(Codex 철학):
   │          워터마크 @핸들 > 메타 업로드일 > 자막 일치 > 지문 일치
   │      · (옵션) Wayback/archive.org 로 공개 시점 교차검증
   │      · 신뢰도 등급 부여 + "더 이른 삭제본 가능" 경고
   │
   └─ F. 리포트
          · 🎬 원본 롱폼: 링크 · 채널 · 업로드일 · 길이
          · 🥇 최초 숏폼화: 링크 · 채널 · 날짜 · 신뢰도 · 근거
          · 🕰️ 타임라인: 파생 쇼츠들 날짜순(누가 언제) — 격차 시각화
          · ⚠️ 한계·미확인 항목 명시
          · report.md / report.json 산출(기존 방식)
```

## 3. 핵심 신규 모듈 (구현 단위)

- `fingerprint.py` — pHash(프레임) + 오디오 지문(fpcalc) + 매칭 스코어러. 순수/도구 주입.
- `derivative_search.py` — 원본으로부터 파생 쇼츠 전수 수집(youtube_client 재사용, 날짜 오름차순).
- `first_shorts_judge.py` — 검증 통과분 날짜순 정렬 + 최초 판정 + 신뢰도 + 근거 우선순위 + 한계 고지.
- `source_finder.py` 확장 — 위 단계들을 잡(job) 파이프라인에 편입(기존 stage 체계 재사용).
- UI: `source_finder.html` 결과에 **🥇 최초 숏폼 패널 + 🕰️ 타임라인** 추가.

## 4. 단계별 로드맵 (Phase)

- **Phase 1 — 파생 수집 + 날짜순 최초 판정(지문 없이, 메타 기반)**
  원본/주제로 YouTube 검색 → 날짜 오름차순 → 가장 이른 후보 + 타임라인. 매칭은 제목·자막 유사도로 1차.
  (빠르게 '실용값' 제공. 신뢰도 MEDIUM 로 표기.)
- **Phase 2 — 지문 매칭(pHash + 오디오)로 검증 격상**
  후보가 진짜 그 롱폼에서 나왔는지 프레임/오디오로 확인 → 신뢰도 HIGH 가능. 우연 일치 제거.
- **Phase 3 — 원본 롱폼 자동 발굴(역이미지·인용구·워터마크)**
  쇼츠만 줘도 원본 롱폼을 찾아 올라감.
- **Phase 4 — 크로스 플랫폼(틱톡/IG/더우인) + Wayback 교차검증**
  플랫폼 간 최초 비교(신뢰도 정직 고지 유지) + 아카이브로 공개시점 보강.

## 5. 실행 환경 (어디서 도나)

- **다운로드·지문·OCR = 사장님 PC**(yt-dlp/ffmpeg/fpcalc 로컬). 웹 컨테이너는 유튜브 차단 → 데모/한계.
- **YouTube 날짜순 검색 = API 키 필요**(쿼터). 키 없으면 데모.
- 기존 `일본쇼츠실행.bat` 서버에 통합(별도 런처 불필요), `🕵️ 원본 소스 찾기` 화면 확장.

## 6.5 ⚠️ 정정 — 입력은 "원본"이 아니라 "사장님이 발견한 쇼츠"

초기 설계가 거꾸로였다. **사장님은 원본을 모른다. 발견한 '쇼츠 1개'만 준다.**
따라서 올바른 흐름:

```
입력: 발견한 쇼츠 URL 1개
 → ① 그 쇼츠 다운로드 → 프레임 지문(dHash) + (선택)오디오 지문
 → ② 같은 콘텐츠 후보 발굴:
       · 프레임 역이미지 검색(구글 렌즈/Bing Visual/SerpAPI) ← 유일한 외부 서비스 의존
       · 자막/제목/화면글자(OCR)/워터마크 @핸들 검색
 → ③ 후보 전부 다운로드 → 프레임 지문 대조(contains) → 진짜 같은 것만 남김
 → ④ 남은 것 날짜순:  가장 이른 롱폼 = 원본,  가장 이른 쇼츠 = 최초 숏폼화(답)
```

**→ 원본은 '찾아내는 것'. 지문으로 역추적해 원본까지 올라간다.**

### 진행 상황
- ✅ **화면 지문 엔진 완성** — `frame_fingerprint.py`(순수 PIL dHash + ffmpeg 프레임 추출).
  밝기·리사이즈·재인코딩에 강건. `contains()`(포함 판정)·`rank_candidates()`(일치순 정렬).
  컨테이너에서 영상→지문 end-to-end 검증(자기대조 coverage 1.0).
- 🔜 **후보 발굴(역이미지 검색)** — 유일하게 외부 서비스 결정 필요:
  · (A) SerpAPI(구글 렌즈) — 유료·간편·정확  · (B) Bing Visual Search API — 무료쿼터
  · (C) 사장님 브라우저로 구글렌즈 반자동  · (D) 텍스트/자막/핸들 검색만(무료·정확도↓)
- 🔜 다운로드·대조 파이프라인 통합(사장님 PC yt-dlp/ffmpeg) → 최초 판정.

## 7. 한 줄 결론

**"반드시 100% 최초"는 세상 데이터의 한계로 아무 도구도 보장 못 한다(정직).
대신 우리는 "지금 찾을 수 있는 가장 이른 파생 쇼츠"를 지문·근거·타임라인으로 제시하고,
불확실성을 숨기지 않고 명시한다 — 이게 실무에서 가장 신뢰받는 방식이다.**
